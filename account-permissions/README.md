# 账号与权限

正式入口 `/operation-workbench/account-permissions/`，个人工作台 `/operation-workbench/account-permissions/member.html`，统一登录 `/login`。

账号、密码哈希、会话、变更申请和审计保存在云端 `/var/lib/xiong-access/accounts.sqlite3`，不提交 GitHub。旧共用管理账号保留作为恢复入口，通过原服务验证密码及旧 Cookie。新账号使用服务端会话；密码用 PBKDF2-SHA256 + 随机盐保存，初始或重置密码只返回一次。停用、权限修改、密码重置撤销旧会话。连续失败登录有频率限制；写请求校验同源与 JSON。

管理员页面真实保存账号，支持角色模板、门店勾选、操作权限、启停、密码重置、配置导出、审计查询。具备账号管理权限的总管理员需要覆盖当前全部门店；普通账号不具备账号管理权。原管理账号不出现在可修改列表中，避免被误停用。

门店目录来自已有稳定目录及直营 / 加盟看板的 `target_stores`；新门店只加入可选目录，不自动授予已有账号。区域归属未确认，按直营 / 加盟分组，并支持逐店选择。原浏览器草稿不会自动变成真实账号，需管理员在新页面重新保存。

新账号进入个人工作台，所有数据、汇总、CSV 导出、汇总问答均由后台按账号、功能和门店筛选。未经适配的原始静态看板、全量 JSON/JS、管理接口和原 Agent 入口对新账号默认拒绝，避免 iframe、直接链接和 AI 绕过。库存展示授权门店的货流，不开放全仓数据。工具通过受控路径访问，需同时具备查看、修改、导出权限，因其在浏览器内完成编辑和文件生成。

**修改与审批的含义：** 修改权限允许提交指定门店的变更申请；审批权限允许审批他人的申请。预算、出价、订货、财务等高风险操作不会因批准而自动执行，批准记录标记为“待正式执行”。原管理账号现有正式操作流程保留。接口不会声称平台已修改或下单成功。

部署：开发验证后推送 GitHub main，在 Mac mini 的干净 main 副本执行 `zsh scripts/deploy_access_control.zsh`。Mac mini 从 GitHub 获取代码，再发布带提交 SHA 的云端版本目录；原服务、数据库、登录态和生产配置不覆盖。独立服务仅监听 127.0.0.1:8020。部署脚本确认健康后，局部修改 Nginx 认证网关及登录路由，保留其他路由，`nginx -t` 后 reload；失败自动回退上一版本。账号数据库独立于发布目录。

验证：`python -m pytest -q tests/test_access_control.py`，`node --test tests/test_account_permissions.mjs`。生产验收需验证旧管理员会话、新账号单门店数据/汇总/导出、无权限路径 403、修改或停用后旧会话 401，并用 Mac mini 浏览器检查正式管理页。
