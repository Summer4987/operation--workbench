# 熊小小 AI 系统拆分与数据安全改造方案

本文档是当前项目后续拆分、部署和外部协作的最高优先级边界说明。目标不是把现有系统继续做成一个大系统，而是从现在开始拆成两套独立产品、两套仓库、两套数据、两套部署。

## 1. 最终目标

### A 系统：熊小小独立 AI 数据系统

定位：内部自用的机密经营系统，不商业化，不交给外部团队深度接触。

包含范围：

- 直营店数据中心。
- 直营店货流中心。
- 直营推广中心。
- 直营订货、库存、出入库、供应商结算、门店结算。
- 老板驾驶舱、内部 AI 分析、经营预警和自动化任务。

安全目标：

- 真实经营数据、品牌财务数据、供应链成本、直营利润口径必须绝对独立和保密。
- 只允许你、核心合伙人和被明确授权的内部人员访问。
- 后续商业化团队默认不得接触 A 系统生产数据、生产配置、数据库、日志、截图和备份。

### B 系统：熊小小 AI 经营管理驾驶舱

定位：未来面向加盟店和中小餐饮商家的商业化产品。

包含范围：

- 门店经营数据中心。
- 门店/加盟经营看板。
- 加盟推广中心。
- AI 经营建议、异常提醒、行动清单。
- 多账号、多角色、多门店和未来 SaaS 化能力。
- 可选的订货、库存或财务辅助模块，但必须使用 B 系统自己的标准化数据模型。

商业化目标：

- 可由专业团队继续开发。
- 可演示、可交付、可复制。
- 不含 A 系统真实数据、财务口径、供应商价格、直营利润和内部策略。

## 2. 硬边界

以下规则必须定死，后续开发、迁移、部署和外部协作都按此执行。

| 编号 | 边界规则 | 说明 |
| --- | --- | --- |
| B1 | A、B 必须是两个 GitHub 仓库 | B 系统未来给专业团队开发，不能和 A 系统共用仓库历史和敏感代码。 |
| B2 | B 系统不能直连 A 系统数据库 | 任何业务理由都不能绕过此规则。 |
| B3 | B 系统不能使用 A 系统真实生产数据做演示 | 演示数据只能使用模拟数据、脱敏样例或 B 系统测试门店数据。 |
| B4 | A 系统财务数据不能进入 B 系统 | 包括收入明细、成本、利润、现金流、供应商价格、真实毛利率、结算规则。 |
| B5 | A 系统生产配置不能进入 B 仓库 | 包括服务器地址、密钥、Token、Cookie、登录态、真实账号、备份路径。 |
| B6 | 外部团队默认只接触 B 仓库 | 如需复用 A 的能力，必须先抽象成无敏感数据的公共组件或重新实现。 |
| B7 | A、B 部署链路独立 | 两套系统独立发布、独立回滚、独立日志、独立备份。 |
| B8 | A 到 B 默认不同步数据 | 如未来确有必要，只能输出脱敏、聚合、不可反推的行业样例数据。 |

## 3. 建议仓库规划

### A 仓库

建议仓库名：

```text
xiongxiaoxiao-private-ai-data-system
```

用途：

- 承载内部机密经营系统。
- 继续遵守 Mac mini 生产主机规则：Mac mini 只运行 GitHub `main` 分支上的已验证代码。
- 存放内部自动化、直营看板、货流、财务、直营推广、生产部署脚本和内部文档。

访问控制：

- 仓库必须私有。
- 只给核心人员最小权限。
- 不邀请商业化外部团队。

### B 仓库

建议仓库名：

```text
xiongxiaoxiao-ai-business-cockpit
```

用途：

- 承载未来商业化的 AI 经营管理驾驶舱。
- 使用模拟数据和标准化业务模型开发。
- 支持后续专业团队协作、产品化、SaaS 化。

访问控制：

- 仓库可以私有起步，后续按商业化团队协作需要开放。
- 外部团队只接触 B 仓库、B 测试环境和 B 测试数据。

## 5. 数据分级

| 等级 | 数据类型 | 系统归属 | 处理规则 |
| --- | --- | --- | --- |
| S4 绝密 | 品牌财务、利润、现金流、供应商真实价格、直营真实成本、结算规则 | 只允许 A | 不进入 B，不给外部团队，不写入演示数据。 |
| S3 敏感 | 直营门店营业额、推广效果、订货数量、库存、评价、平台账号配置 | 只允许 A | B 只能使用模拟或聚合样例。 |
| S2 内部 | 通用经营指标结构、门店经营分析方法、报表布局、非敏感字段模型 | A/B 可复用 | 复用前去品牌化、去真实数据、去生产配置。 |
| S1 通用 | UI 组件、图表组件、基础导入导出、空白模板、测试框架 | A/B 可复用 | 可抽成公共代码，但不能夹带真实数据。 |

## 6. 拆分路线

### 第 0 阶段：冻结边界

目标：先把拆分规则固定下来，避免后续继续往一个系统里混加能力。

交付物：

- 本文档。
- A/B 仓库命名和权限策略确认。
- 当前仓库只作为拆分源仓库，不再默认承载所有新商业化能力。

### 第 1 阶段：建立两个仓库

目标：从现在开始形成物理隔离。

动作：

1. 创建 A 仓库 `xiongxiaoxiao-private-ai-data-system`。
2. 创建 B 仓库 `xiongxiaoxiao-ai-business-cockpit`。
3. A 仓库保留当前生产系统所需代码和文档。
4. B 仓库只放产品化驾驶舱骨架、通用组件、模拟数据和安全的产品文档。
5. 两个仓库分别配置 `.gitignore`，禁止提交日志、浏览器 profile、下载文件、截图、生产密钥和真实数据。

验收标准：

- 外部团队即使拿到 B 仓库，也看不到 A 的生产代码、历史数据和敏感配置。
- A 仓库可以继续支持 Mac mini 从 `main` 拉取部署。
- B 仓库可以本地启动或预览，但只使用模拟数据。

### 第 2 阶段：A 系统加固

目标：先保护内部机密系统。

动作：

1. 将直营数据、直营货流和直营推广统一归入 A 系统导航和文档。
2. 检查订货、货流、推广脚本是否存在对外暴露入口。
3. 梳理生产配置来源，逐步从代码中迁出真实密钥和敏感地址。

验收标准：

- B 系统无法访问 A 数据库。
- A 内部订货和货流可以继续协同。

### 第 3 阶段：B 系统产品化骨架

目标：让商业化驾驶舱从第一天就使用干净模型。

动作：

1. 建立 B 系统的门店、账号、角色、租户、经营指标和推广指标基础模型。
2. 用模拟数据搭建门店经营首页、推广首页、AI 建议页。
3. 仅迁移无敏感的 UI 组件、图表组件和报表结构。
4. 不迁移 A 的生产脚本、生产配置、财务字段、供应商价格、直营门店明细。
5. 为外部团队准备 `README`、开发环境和模拟数据说明。

验收标准：

- B 系统能独立运行。
- B 系统没有 A 的真实数据和真实生产配置。
- B 系统的数据模型可以支持未来加盟店和 SaaS 化。

### 第 4 阶段：通用能力抽象

目标：让两套系统可以共享方法，但不共享秘密。

可抽象能力：

- 基础 UI 组件。
- 图表组件。
- 空白导入模板。
- 通用任务状态模型。
- 通用 AI 建议结构。
- 通用报表导出。

不可抽象进入 B 的能力：

- 财务利润计算的真实口径。
- 直营推广预算策略。
- 供应商结算规则。
- 直营门店真实经营数据。
- 平台账号、Cookie、Token、验证码处理现场。

## 7. 立即执行清单

| 优先级 | 任务 | 结果 |
| --- | --- | --- |
| P0 | 确认本文档作为拆分边界 | 后续所有开发按 A/B 两仓库处理。 |
| P0 | 创建两个 GitHub 私有仓库 | 形成物理隔离。 |
| P0 | 在当前仓库保留拆分源，禁止新增 B 商业化功能到 A 主看板 | 防止继续混合。 |
| P0 | 盘点生产密钥、账号、日志、截图和真实数据 | 防止迁移时泄露。 |
| P1 | 生成 A 仓库首版目录 | 保证 Mac mini 生产链路不中断。 |
| P1 | 生成 B 仓库首版产品骨架 | 给未来专业团队一个干净起点。 |
| P1 | 为 B 构造模拟数据 | 所有演示和开发只用模拟数据。 |
| P2 | 从 A 中抽离通用 UI/图表/AI 建议结构 | 只迁移无敏感通用能力。 |
| P2 | 完成 A 内部财务和订货数据链路梳理 | 财务独立但可读取 A 内部订货结算数据。 |

## 8. 外部团队协作规则

外部团队可接触：

- B 仓库。
- B 测试环境。
- B 模拟数据。
- B 产品需求文档。
- 已脱敏的通用 UI、报表和 AI 建议模板。

外部团队不可接触：

- A 仓库。
- A 生产数据库。
- A 服务器生产配置。
- A 浏览器登录态、Chrome profile、Cookie 和验证码现场。
- 直营店真实经营数据。
- 供应商价格、成本、利润、现金流和结算规则。
- Mac mini 生产主机的本地运行产物、日志、截图和下载数据。

## 9. 拆仓前检查清单

每次从当前项目复制或迁移文件到 B 仓库前，必须逐项检查：

- 文件是否含真实门店经营数据。
- 文件是否含财务字段、成本、利润、供应商价格。
- 文件是否含服务器地址、Token、Cookie、账号、密钥。
- 文件是否含真实平台账号、真实推广预算、真实出价策略。
- 文件是否含生产路径、Mac mini 本地路径、浏览器 profile 路径。
- 文件是否含日志、截图、导出文件或历史运行结果。
- 文件是否含品牌内部制度、合同条款或商业策略。

只要任意一项为“是”，默认不得进入 B 仓库；必须脱敏、重写或只保留抽象结构。

## 10. 当前结论

下一步应先创建两个私有 GitHub 仓库，然后把当前项目作为拆分源：

- A 仓库优先保证现有生产能力不断、财务和直营数据安全。
- B 仓库从干净产品骨架开始，不继承 A 的真实数据和敏感历史。

这条路线会牺牲一点短期开发速度，但能最大程度避免未来商业化团队、加盟端和内部绝密经营系统之间发生数据混淆。
